# Bare-Metal Server-Grade Unified Roadmap

> **Active roadmap:** this is the single active architecture route for driving OMFS toward real bare-metal server-grade high-load behavior.

## Mission

- [ ] Drive OMFS toward sustained throughput close to the physical disk ceiling (`~7000 MB/s` target class for this machine).
- [ ] Drive foreground latency for `delete`, `write`, `read`, and `create` toward the minimum practical value, with hot-path target pressure toward `5-10ms` where semantics and hardware allow.
- [ ] Prefer architecture replacement over local patching whenever old paths preserve weak serialization, foreground fences, global locks, or hidden durable waits.
- [ ] Keep every major claim backed by structural contracts, debug build, SMP runtime evidence, and `docs/journal/OMFS_SERVER_EXECUTION_JOURNAL_v0.2.md`.

## Non-Negotiable Level-0 Architecture Contract

- [ ] Foreground hot paths publish semantic intent and return after the minimum safe visibility/detach boundary.
- [ ] Heavy durable work runs in event-driven asynchronous planes: retire, writeback, allocation, checkpoint, and block IO completion.
- [ ] Strict durability waits exist only behind explicit strict contracts such as `sync`/`fsync`.
- [ ] Normal foreground `delete`, `write`, `read`, and `create` do not hide sync-wave, checkpoint, retire, or full writeback waits.
- [ ] Foreground visibility/publication must not depend on synchronous barrier admission or deferred `sync-wave` completion; visibility is an event-driven ownership/publication contract, not a disguised barrier.
- [ ] No global lock, global cache, global append lock, global single queue, or coarse process-wide serialization is introduced on a hot path.
- [ ] Hot state is sharded by file, entry, lane, region, queue, CPU, NUMA node, or cache-ownership domain.
- [ ] Every long operation has an owner, epoch/ticket, bounded progress event, terminal status propagation, and diagnostic phase attribution.
- [ ] Busy-wait/yield loops are not used as an architecture; waiting is event-driven unless it is a documented short hardware-level spin with a proven bound.
- [ ] Regressions against stronger event-driven contracts are fixed by strengthening the surrounding architecture, not by restoring old foreground waits.
- [ ] If a deferred-barrier or deferred `sync-wave` design is slower than the non-barrier route, the fix is to redesign visibility/publication ownership itself through async epochs/events and sharded publication state, not to move the same barrier later in time.
- [ ] Crash consistency comes from intent records, ordered publication, checkpoint proofs, and replayable state, not from blocking the foreground API until all cleanup is physically complete.
- [ ] Intent records live in one authoritative ordered intent/WAL stream with explicit plane/type tags and replay ordering; ad-hoc side journals that can diverge from publication/checkpoint order are forbidden on normal hot paths.
- [ ] Replay semantics are explicit: if delete/create/write publication is durable but downstream retire/reclaim/apply is incomplete at crash time, replay reconstructs the pending work and finishes it asynchronously without resurrecting logically detached namespace state.
- [ ] Mount acceleration comes from a dual-copy checkpoint snapshot frontier plus bounded WAL tail replay; the snapshot is a checked acceleration/proof surface, while the ordered WAL remains the authoritative source for post-frontier progress.
- [ ] Checkpoint snapshot publication is a background checkpoint-owner responsibility driven by operation count, elapsed time, WAL-tail length, dirty metadata pressure, clean shutdown, or explicit strict sync/fence policy; normal foreground transactions must never synchronously rewrite checkpoint snapshots.
- [ ] File writeback uses one unified sharded dirty-extent engine for small and large files; no permanent separate `large-file`/`small-file` hot-path architecture is allowed.
- [ ] Dirty extents are file-size agnostic: files from a few bytes to petabyte-class ranges are represented as bounded byte-range work units, never as one monolithic file-sized operation.
- [ ] Dirty work units are dynamic and capability-aware: their size and dispatch shape come from dirty pressure, latency SLA, device queue capability, DMA/PRDT limits, alignment, cache locality, and contending metadata/delete/create pressure, not from fixed magic chunk classes.
- [ ] Throughput-mode IO must coalesce adjacent dirty extents and block requests into capability-derived batch windows large enough to amortize submission/completion overhead; the effective floor is measured from `preferredTransferSectors`, `maxTransferSectors`, queue depth, DMA/PRDT/bounce limits, CPU/cache topology, and runtime evidence, not hard-coded as any universal byte threshold.
- [ ] CPU wakeups must be completion-batched: steady-state throughput paths may not wake or reschedule a CPU for every micro-request; they must use lane-local completion harvesting, interrupt moderation, or bounded hybrid poll/interrupt ownership selected by backend capability and latency SLA.
- [ ] Fixed-size arrays such as runlist/span/request capacities are allowed only as cache-friendly per-node/request-node storage; they must never become file-size, operation-size, or fragmentation-count limits. Large and petabyte-class files must progress through cursor/continuation/chained batch-nodes until the full range is complete.
- [ ] Legacy monolithic raw-file write/read paths are removed or reduced to bootstrap/direct diagnostic fallbacks once dirty-extent ownership is authoritative.
- [ ] Hot-path dirty-extent descriptors, intent records, mapping tickets, completion tokens, and publication receipts are allocated from bounded per-lane/per-CPU pools or arenas, not from a global allocator on the foreground path.
- [ ] Boot handoff system ranges and system-first memory reservation are non-negotiable: boot/kernel/loader/BootInfo/memory-map/framebuffer/BOOTRAM/ACPI-RSDP/process/thread/stack/pool ownership is protected before any FS/cache/I/O allocation, and FS/cache/I/O scratch planes may use only explicit leftover allocatable RAM with fail-closed exhaustion and no overlap with system ranges.
- [ ] The physical RAM ownership map is explicit and authoritative: `docs/SUBSYSTEM/kernel_memory_address_map.md` is the source of truth for boot/kernel/system ranges versus FS/cache/I/O scratch planes, and disk-layout values such as OMFS LBA offsets must never be mistaken for RAM addresses.
- [ ] Diagnostic and telemetry paths are architecture surfaces: they must be compile-gated or policy-gated, bounded, nonblocking, and targeted, and must never create a hidden serial/logging bottleneck that changes SMP timing or masks the workload being measured.

## Formal Lifecycle Models

- [ ] `Formal Lifecycle Models` are the single authoritative semantics/state-machine layer for OMFS/FileIO behavior in this roadmap.
- [ ] All architecture work in phases `1-8` must map to explicit lifecycle models; code paths that do not fit one of the formal models below are architectural debt and must fail-close or be redesigned instead of being normalized as ad-hoc behavior.
- [ ] Each lifecycle model below is normative and must explicitly define: authoritative owner, allowed state transitions, foreground boundary, forbidden foreground work, background-only work, crash/replay point, terminal completion condition, telemetry points, and contract tests.
- [ ] No implementation may silently invent a second lifecycle for the same API surface; if a new state or transition is needed, the roadmap and the matching contract tests must be updated first.
- [ ] `Execution Order`, `Phase`, `Required Architecture`, and `Required Work` sections are implementation slices only; they may decompose, schedule, or localize lifecycle obligations, but they must not redefine semantics, introduce alternative state machines, or weaken lifecycle boundaries.
- [ ] `Anti-Regression Contracts` exist to verify the lifecycle models and the level-0 architecture contract, not to create a second normative contract layer; if a contract and a lifecycle model diverge, the contract must be corrected to the lifecycle model.
- [ ] `Current checkpoint` text is observational status only: it may describe what is implemented, open, or still weak, but it must never be treated as normative behavior or as permission to preserve a weaker path.
- [ ] If wording in any later section appears to conflict with a formal lifecycle model, the lifecycle model wins and the downstream section must be rewritten to match it.
- [ ] Downstream sections should reference lifecycle states and ownership seams by name instead of restating full semantics, so the roadmap stays unified instead of forking into duplicate contract narratives.

### Write Lifecycle

- [ ] `submit -> semantic publication -> dirty-extent ownership -> prepared mapping -> physical dispatch -> completion delivery -> durability frontier`
- [ ] Authoritative owner flow: caller/request ticket owns submit, dirty-extent lane owns publication/runtime writeback, prepared mapping authority owns logical-to-physical planning, block IO/data-plane owns physical dispatch, completion delivery owns terminal request status, durability frontier/checkpoint ownership owns strict durability proof.
- [ ] Allowed state transitions are monotonic and explicit; write requests may advance only through the ordered lifecycle above and may not jump from submit to direct physical fallback, hidden sync completion, or wrapper-private write path.
- [ ] Foreground boundary for normal write is semantic publication into dirty-extent ownership, not physical media completion and not durability completion.
- [ ] Forbidden in foreground: global writeback drain, direct `driver->Write(...)` fallback, checkpoint wait, retire wait, full allocator reclaim, hidden `sync`/`fsync`, or any second raw-direct write architecture.
- [ ] Background-only work: prepared mapping, physical dispatch, completion routing, durability frontier advancement, checkpoint proof progression, and replay-driven continuation.
- [ ] Crash/replay point: after semantic publication but before durability frontier completion, replay reconstructs writeback/durability work from authoritative intent/publication state without requiring foreground repair hacks.
- [ ] Terminal completion condition: request-owned terminal status is delivered exactly once for the write request's execution contract, while durability frontier remains a separate observable boundary unless strict sync was explicitly requested.
- [ ] Large/fragmented write mapping is cursor-based: if one prepared mapping node reaches its span/request capacity, it completes a valid prefix and publishes a continuation instead of returning overflow, allocating a file-wide plan, or expanding the kernel stack.
- [ ] Telemetry points and contract tests must cover at minimum: submit, publish, mapping, physical dispatch, completion delivery, durability lag/frontier, bytes per extent, queue depth, and blocked foreground wait time.

### Read Lifecycle

- [ ] `submit -> cache resolution -> physical read dispatch -> completion delivery`
- [ ] Authoritative owner flow: caller/request ticket owns submit, cache-resolution/read-path owner owns hot-cache decision, block IO/data-plane owns cold read dispatch, completion delivery owns terminal request status.
- [ ] Allowed state transitions are monotonic and explicit; reads may not route through hidden writeback drain, shared-cursor choreography, or fake async wrappers around a second execution engine.
- [ ] Foreground boundary for native async read is request acceptance plus authoritative `STATUS_PENDING`; blocking wrappers may wait, but they must wait on this same lifecycle instead of owning another path.
- [ ] Forbidden in foreground: global cache serialization, hidden metadata barrier, direct dependency on mutable shared cursor state after submit, and any completion-path filesystem work.
- [ ] Background-only work: cold-path physical dispatch, device completion, terminal delivery, and request recycle.
- [ ] Crash/replay point: read requests themselves are not durable authority; crash consistency for read comes from the underlying durable metadata/data state, not from replaying transient request objects.
- [ ] Terminal completion condition: request-owned buffer population or EOF/error status is delivered exactly once through the authoritative completion route.
- [ ] Telemetry points and contract tests must cover at minimum: cache-hit versus cold-read split, submit-to-dispatch, physical read latency, delivery latency, queue depth, and shared-cursor rejection tests.

### Delete Lifecycle

- [ ] `intent publish -> namespace detach -> retire queue ownership -> reclaim/apply -> checkpoint proof`
- [ ] Authoritative owner flow: delete caller/delete ticket owns intent publish, namespace publication owner owns detach visibility, retire owner owns reclaim work, allocator/reclaim owner owns free-space mutation, checkpoint/durability owner owns final proof.
- [ ] Allowed state transitions are monotonic and explicit; delete may not regress from detached namespace state back to visible namespace state because downstream retire/reclaim has not completed yet.
- [ ] Foreground boundary for normal delete is intent publication plus namespace detach, not cluster release completion, bitmap completion, or checkpoint completion.
- [ ] Forbidden in foreground: full dirty-entry drain as delete conflict resolution, synchronous reclaim/apply completion, bitmap free completion wait, and durability tail masquerading as normal delete success.
- [ ] Background-only work: retire queue service, reclaim/apply, allocator mutation, checkpoint proof completion, and replay-driven requeue after crash.
- [ ] Crash/replay point: if delete intent and detach/publication proof are durable before crash, replay must preserve the logical deletion and resume retire/reclaim asynchronously without resurrecting namespace state.
- [ ] Terminal completion condition: normal delete API success is achieved at the detach boundary; background reclaim/checkpoint completion is a separate state machine and not a foreground success prerequisite unless an explicit strict durability contract says otherwise.
- [ ] Telemetry points and contract tests must cover at minimum: intent publish, detach, retire queue delay, reclaim/apply time, checkpoint lag, and replay-after-detach correctness.

### Create Lifecycle

- [ ] `metadata reservation -> namespace publication -> async durable apply`
- [ ] Authoritative owner flow: create caller/create ticket owns metadata reservation request, publication owner owns namespace visibility, allocator/metadata plane owns durable apply and any deferred extent allocation or metadata growth.
- [ ] Allowed state transitions are monotonic and explicit; create may not fork into a second synchronous metadata path just to satisfy wrapper semantics.
- [ ] Foreground boundary for normal create is successful namespace publication after the minimum required reservation/proof work, not full durable apply completion.
- [ ] Forbidden in foreground: global allocator stall, hidden checkpoint tail, full reclaim wait, and wrapper-private metadata commit path.
- [ ] Background-only work: deferred durable metadata apply, extent materialization, checkpoint proof progression, and replay-driven completion if crash interrupts the durable tail.
- [ ] Crash/replay point: after namespace publication but before durable apply completion, replay must complete or roll forward the durable create work from authoritative intent/proof state without duplicating or reviving conflicting namespace entries.
- [ ] Terminal completion condition: normal create success is tied to the chosen namespace publication contract; durable completion stays separately observable unless strict sync semantics were explicitly requested.
- [ ] Telemetry points and contract tests must cover at minimum: reservation latency, publication latency, durable apply lag, allocator pressure, and replay correctness after published-but-not-fully-applied create.

### Sync / Fsync Lifecycle

- [ ] `explicit strict boundary -> progress/drain proof -> durability submission -> completion`
- [ ] Authoritative owner flow: strict caller/sync ticket owns the explicit boundary request, drain/progress owner owns proving the relevant dirty set has reached the contract boundary, durability owner owns submission to the backend frontier, completion/proof owner owns terminal success or failure.
- [ ] Allowed state transitions are monotonic and explicit; strict sync may wait only on the write set and durability frontier required by the contract and may not absorb unrelated namespace repair, reclaim, or hidden global cleanup.
- [ ] Foreground boundary is intentionally blocking here because `sync`/`fsync` are explicit strict APIs; they are the exception, not the normal model.
- [ ] Forbidden in foreground even for strict sync: hidden recovery loops as normal semantics, global unrelated drains, second residual no-wait tails after an authoritative progress/drain proof, and wrapper-private raw write path.
- [ ] Background-only work may still execute the actual data-plane completions and checkpoint advancement, but strict sync waits only on the explicit proof frontier defined by the API contract.
- [ ] Crash/replay point: success means the requested durability frontier is proven; replay after crash must not need an emergency foreground repair path to explain a previously reported strict success.
- [ ] Terminal completion condition: the requested durability frontier or barrier proof is reached and reported exactly once with explicit failure attribution when it is not.
- [ ] Telemetry points and contract tests must cover at minimum: drain/progress phase, acquire phase, wait phase, barrier/direct fallback phase, total strict-sync latency, and no-residual-tail enforcement.

### Checkpoint Snapshot / Mount Replay Lifecycle

- [ ] `select newest valid checkpoint slot -> validate checksum/generation/frontier -> bounded WAL tail replay -> requeue incomplete async work -> publish mounted runtime state`
- [ ] Authoritative owner flow: mount reader owns slot selection and validation, WAL/replay owner owns all post-frontier authoritative state, checkpoint owner owns asynchronous snapshot publication, lifecycle owners requeue incomplete delete/create/write/reclaim/apply work after replay.
- [ ] Allowed state transitions are monotonic and explicit: a checkpoint snapshot may advance only to a WAL/checkpoint frontier whose intent records and durable metadata proof are complete, and mount may only trust a slot after generation, checksum, feature compatibility, checkpoint LSN, and frontier invariants validate.
- [ ] Foreground boundary is unchanged: normal delete/create/write transactions append authoritative intent/WAL progress and return at their lifecycle boundary; they may request checkpoint work but must not synchronously publish checkpoint snapshot slots.
- [ ] Forbidden in foreground: rewriting either checkpoint snapshot slot, scanning the full WAL to avoid maintaining a checkpoint frontier, using snapshot state as a second authority that can diverge from WAL order, or hiding checkpoint publication behind normal create/delete/write success.
- [ ] Background-only work: checkpoint frontier selection, inactive-slot materialization, checksum/hash sealing, generation flip, old-slot retirement, WAL truncation eligibility proof, replay-window compaction, and clean-shutdown checkpoint publication.
- [ ] Crash/replay point: after power loss, mount selects the newest valid slot among two independent checkpoint copies, rejects torn or incompatible slots by checksum/generation/frontier validation, replays WAL from the selected `checkpoint_lsn`, and resumes incomplete async work without foreground repair hacks.
- [ ] Terminal completion condition: mount completes when a valid checkpoint base plus replayed WAL tail produces one authoritative runtime state; if neither slot validates, mount fails closed or enters an explicit recovery mode rather than guessing from partial snapshot bytes.
- [ ] Telemetry points and contract tests must cover at minimum: selected slot, rejected slot reason, generation, checkpoint LSN, replay start/end LSN, WAL tail bytes/records, replay duration, requeued async work counts, snapshot publication cadence, slot checksum failures, and clean-shutdown snapshot proof.

### Async Request Lifecycle

- [ ] `request acquire -> ownership token/ticket -> pending -> execution -> terminal completion -> recycle`
- [ ] Authoritative owner flow: request pool/descriptor acquisition owns initial object lifetime, public request ticket owns caller-visible authority, execution plane owns request progress, completion delivery owns terminal status publication, recycle path owns deterministic descriptor return to bounded storage.
- [ ] Allowed state transitions are monotonic and explicit; requests may not skip `pending`, may not emit more than one terminal completion, and may not be resurrected after recycle.
- [ ] Foreground boundary for native async APIs is authoritative request acquisition plus `STATUS_PENDING` publication, not hidden execution completion.
- [ ] Forbidden in foreground: hidden synchronous wait before `STATUS_PENDING`, dependence on caller stack lifetime after submit without explicit staged/pinned ownership contract, and execution work inside completion delivery.
- [ ] Background-only work: request execution, physical IO, completion routing, cancel resolution, terminal publication, and descriptor recycle.
- [ ] Crash/replay point: transient async request objects are not durability authority; replay responsibility belongs to the underlying write/delete/create lifecycles and their intent/publication state, not to ephemeral request ids alone.
- [ ] Completion delivery isolation is strict: once a request enters terminal publication, delivery becomes allocation-free and filesystem-free; any mapping/replan/checksum/commit/reclaim/writeback continuation must already be finished or queued to an explicit next owner before terminal status is published.
- [ ] Terminal completion condition: exactly one terminal packet/event/APC/status publication is emitted, after which the request descriptor is recycled deterministically into bounded storage.
- [ ] Telemetry points and contract tests must cover at minimum: submit rate, queue depth, pending duration, execution latency, delivery latency, cancel latency, recycle latency, and one-terminal-completion enforcement.

### Blocking Wrapper Lifecycle

- [ ] `submit -> wait -> return`
- [ ] Authoritative owner flow: wrapper call owns only the caller-facing wait; the underlying request/ticket, execution, completion, and durability ownership remain in the same authoritative engine used by native async callers.
- [ ] Allowed state transitions are monotonic and explicit; wrappers may only submit into the authoritative async lifecycle, wait on its terminal/proof condition, and return the same resulting semantics.
- [ ] Foreground boundary is wrapper-specific blocking behavior only; it must not imply a second execution engine, a second allocator path, or a second publication/durability model.
- [ ] Forbidden in foreground: wrapper-private `ReadFile(...)` / `WriteFile(...)` execution path, duplicate allocator/writeback/ownership/publication/replay/durability logic, and fake-nonblocking API surfaces backed by blocking internals.
- [ ] Background-only work is identical to the native async/request lifecycle and is not redefined by the wrapper.
- [ ] Crash/replay point is inherited from the underlying authoritative lifecycle; wrappers introduce no additional durable state machine.
- [ ] Terminal completion condition: wrapper return is driven by the exact same terminal status or explicit durability proof used by the underlying request contract.
- [ ] Telemetry points and contract tests must cover at minimum: wrapper submit cost, wrapper wait time, semantic parity with native async submission, and rejection of any second private blocking execution engine.

## Global Targets

- [ ] `delete`: move from current hundreds of milliseconds toward tens of milliseconds, then target `5-10ms` foreground semantic latency through `publish intent + detach namespace + async retire`.
- [ ] `write`: remove foreground writeback fences and approach backend throughput through sharded writeback, write-combining, bounded quanta, DMA/multiqueue readiness, and zero/min-copy where possible.
- [ ] `read`: make cache-hot reads low-ms and make cold/sequential reads limited by block IO queue depth instead of metadata/cache serialization.
- [ ] `create`: make hot-path create low-ms through prepared metadata buffers, pooled records, async durable apply, and no hidden sync commit tail.
- [ ] `throughput`: push toward the `~7000 MB/s` disk-class ceiling after OMFS serialization is removed and block IO/DMA/multiqueue capacity is proven.
- [ ] `latency`: always separate foreground semantic latency from durable cleanup latency and optimize foreground first without weakening correctness.
- [ ] `mount`: make normal boot/mount time proportional to checkpoint age and WAL tail length, not total filesystem size, while preserving fail-closed crash recovery through dual checkpoint slots and ordered WAL replay.

## Phase 2: Retire / Free Intent / Replay / Allocator Plane

### Goal

- [ ] Prevent allocation/free/release work from serializing foreground APIs.

### Required Architecture

- [ ] Free operations become intent records with asynchronous retirement where semantics allow.
- [ ] Release operations become intent records with asynchronous retirement where semantics allow.
- [ ] Delete retire, free-intent, allocator reclaim, and checkpoint visibility proofs share one ordered intent/WAL authority instead of independent ad-hoc journals.
- [ ] Replay can reconstruct retire, free-space mutation, allocator reclamation, and checkpoint completion work from durable intent/WAL state plus publication proofs.
- [ ] Mount starts from the newest valid dual checkpoint snapshot slot and replays only the bounded WAL tail after that slot's `checkpoint_lsn`.
- [ ] Checkpoint snapshots are double-buffered with independent slot identity, generation number, feature compatibility, checkpoint LSN, frontier proof, and checksum/hash over the complete serialized snapshot.
- [ ] Checkpoint snapshot cadence is policy-driven by transaction count, elapsed time, WAL-tail length, dirty metadata pressure, clean shutdown, and explicit strict durability requests; it is never a per-transaction foreground rewrite.
- [ ] If a delete intent is durable and namespace detach/publication proof is durable before crash, replay preserves the logical deletion and requeues reclaim/retire work instead of reviving the namespace entry.
- [ ] Reclaim/release completion is idempotent under replay and can safely resume from partial progress.
- [ ] Intent ownership carries epoch/ticket identity so replay can reject stale duplicate work instead of re-running blind mutation.
- [ ] Free-space state is sharded by region/lane.
- [ ] Allocator state is sharded by region/lane.
- [ ] Retire owners process bounded batches.
- [ ] Retire owners publish progress tickets/events.
- [ ] Backpressure exposes dirty bytes.
- [ ] Backpressure exposes retire backlog.
- [ ] Backpressure exposes free intent backlog.
- [ ] Backpressure exposes allocator region pressure.
- [ ] Backpressure exposes checkpoint pressure.
- [ ] Reclaim is replayable after crash.

## Phase 3: Write Path And Sharded Writeback Plane

### Goal

- [ ] Make write throughput scale toward disk capacity while keeping foreground write latency bounded.
- [ ] Replace legacy monolithic file-range writeback with a unified sharded dirty-extent engine that serves small and large files through the same ownership model.

### Required Architecture

- [ ] Foreground write appends/copies into sharded writeback ownership and returns after semantic publication unless strict sync is requested.
- [ ] Writeback workers own entries by exact epoch and lane.
- [ ] Write-combining happens per lane/extent without a global append lock.
- [ ] Dirty extents are the unit of ownership, progress, reclaim, and completion; files are not treated as one monolithic block-task.
- [ ] Dynamic work-unit sizing replaces fixed `large-file`/`small-file` paths.
- [ ] Dynamic work-unit sizing uses block-device capability (`nativeQueueDepth`, `maxTransferSectors`, DMA/PRDT/bounce limits), dirty backlog, dirty age, active waiters, delete/create contention, cache/NUMA locality, and current queue pressure.
- [ ] Writeback quanta are large enough for throughput when uncontended because the scheduler coalesces adjacent extents by lane and device capability.
- [ ] Writeback quanta are small and deterministic under delete/create metadata contention because the scheduler shrinks/rotates work units by pressure and progress events, not by hard-coded file-size classes.
- [ ] Writeback completion publishes progress events for metadata/delete-retire waiters.
- [ ] Dirty pressure wakes workers through event-driven lanes, not foreground drains.
- [ ] Completion owns each dirty extent terminal status and publishes it through event-driven completion lanes.
- [ ] Dirty-extent descriptors, prepared mapping tickets, and writeback completion tokens come from bounded per-lane/per-CPU pools with deterministic recycle, not `Kmalloc` on the hot write path.
- [x] Public non-blocking FileIO uses an explicit submission/completion contract: `SubmitRead(offset,len,buffer,token)`, `SubmitWrite(offset,len,buffer,token)`, `SubmitAppend(len,buffer,token)`, `Poll/Wait/Cancel(token)` or equivalent typed APIs; fake async wrappers around blocking `ReadFile(...)` / `WriteFile(...)` are forbidden.
- [x] Sync and async FileIO APIs converge into one internal submission/completion engine; a second hidden blocking execution engine for `WriteFile(...)` / `ReadFile(...)` is forbidden.
- [x] Async read/write requests carry explicit per-request offset or append authority; the async hot path must not derive request ownership from shared live `fsHandle->cursor`.
- [x] Async write submission returns after semantic publication into dirty-extent ownership unless strict sync/durable completion is explicitly requested; device completion and durability completion stay in asynchronous planes.
- [x] Async read completion is event-driven and request-owned; blocking `ReadFile(...)` is a compatibility surface, not the architecture model.
- [x] Blocking `WriteFile(...)` / `ReadFile(...)` are only compatibility wrappers of the form `submit -> wait -> return` over the same internal request engine; they must not own private allocator, writeback, ownership, publication, replay, or durability logic.

- [x] User buffer lifetime is explicit on async submit: either bounded staged ownership or pinned/borrowed ownership with deterministic release; no async request may depend on caller stack lifetime after submit returns.
- [x] Append ordering is owned by an explicit append-publication seam, not by one shared file cursor and not by a global append lock.
- [x] Native async callers may chain `QueueWrite/QueueRead/Append/Fence/Completion` or equivalent submission/fence primitives on one authoritative engine; wrapper APIs must not fork behavior or semantics away from that engine.
- [x] Completion delivery is a pure terminal-publication path: completion callbacks/APCs/port packets/events may publish terminal status, wake waiters, and enqueue the next owner or follow-up ticket, but they must not execute filesystem work such as allocation, replay, reclaim, writeback, flush, metadata mutation, or hidden re-entry into the IO engine.
- [x] Completion delivery is also micro-bounded and allocation-free: completion workers must stay on `publish terminal status -> wake waiter -> queue next owner -> recycle bounded request state`, and may not acquire writeback pooled storage, metadata scratch, mapping leases, allocator leases, or any other filesystem execution resources.
- [ ] Fail-closed unsupported nonresident conversion shapes are a safety boundary, not an acceptable steady-state large-file architecture; closure requires typed prepared mapping/conversion ownership for sparse extents, fragmented extents, cluster-boundary overlaps, and mixed remap/extend cases.
- [ ] All nonresident conversion paths must converge on one authoritative contract: `map -> replan -> async physical dispatch -> completion-owned commit`, carrying exact mapping epoch, logical byte-range authority, physical span authority, sparse/hole intent, and fragment ordering so stale replans cannot commit corrupted disk state.
- [ ] Legacy direct/raw file-range submission is retained only for bootstrap/direct diagnostic use until removed behind the dirty-extent engine.
